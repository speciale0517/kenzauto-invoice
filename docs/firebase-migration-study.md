## 現状（2026-10-07時点）

- `index.html` 1ファイルで完結。保存先はlocalStorage（プレフィックス`ken_`）
- 保存キー：`ken_shop` / `ken_ledger` / `ken_customers` / `ken_vehicles` / `ken_templates` / `ken_lastbackup`
- 各データを配列・オブジェクトごと丸ごと`JSON.stringify`して`setStoreItem()`で保存（`saveLedgerToStorage()`等）
- localStorageの上限は約5MB。`estimateStorageUsageBytes()`で4MB超過時に警告
- 伝票No・お客様コードは高水位マーク（`shop.invoiceSeq` / `shop.customerSeq`）で採番

## Firebase（Cloud Firestore）無料枠（Sparkプラン）

| 項目 | 無料枠 |
|---|---|
| 保存容量 | 1 GiB |
| 読み取り | 50,000回/日 |
| 書き込み | 20,000回/日 |
| 削除 | 20,000回/日 |
| 通信量 | 10 GiB/月 |
| 1ドキュメント最大サイズ | 1 MiB（一般に知られている仕様。今回は未確認） |

- 無料枠を超えるとその日は使えなくなる。Blazeプラン（従量課金）にも同じ無料枠が付き、超えた分だけ課金
- Cloud Storage（画像などのファイル保存）は2026-02-03以降Blazeプラン必須（5GBまで無料）
- **公式ページはこの環境から開けず、第三者のまとめサイトで確認した値。設計前に公式の料金ページで再確認すること**
- 試算：請求書1件を数KBとすると年1,000件で数MB。容量は問題にならない。読み取り回数は、毎回全件を読み込む作りにしないこと（キャッシュ前提）

## メリット

1. 複数の端末（PC・iPad・スマホ）でデータを共有できる
2. 端末の故障や買い替え、Safariのデータ消去、iOSによる自動削除でデータが消えなくなる
3. 容量の心配がほぼなくなる
4. 共同利用や、派生版（`kzs_`）の複数店舗対応へ広げやすい

## デメリット・リスク

1. ネット接続が前提になる。オフライン中に複数の端末で同時に編集すると、データがぶつかる
2. Firebaseのログイン機能はfile://では動かないため、Firebase Hosting等での公開とログインが必要になる
3. セキュリティルールを誤ると顧客の個人情報（氏名・電話番号・住所）が外部から丸見えになる（最大のリスク）
4. Googleの料金・仕様変更に依存する
5. 台帳は1件ずつのドキュメントに分割して保存する作りへの変更が必要（1MiB上限）。採番も複数の端末で同時に使っても番号が重ならない処理（トランザクション等）に作り直す必要がある
6. Playwrightのテストに、Firebaseのテスト用環境（エミュレータ）を組み込む必要がある

## 設計案（Claudeからの提案・未確定。次回セッションで確認して確定）

### A. Firestoreのデータ構造（項目4）

1店舗＝1つの`shops/{shopId}`配下に集約する。`shopId`を最初から持たせておくと、派生版や複数店舗にも流用できる。

```
shops/{shopId}                     店舗設定（現ken_shop）＋採番カウンタ(invoiceSeq/customerSeq)＋allowedEmails（利用許可メール）
  invoices/{invoiceId}             請求書・見積書（現ken_ledgerの1件＝1ドキュメント。totalsスナップショット含む）
  customers/{customerId}           顧客（現ken_customers）
  vehicles/{vehicleId}             車両（customerIdを持たせる。車検リマインドを顧客横断で検索するため独立コレクション）
  settings/templates               定型文（現ken_templates。小さいので1ドキュメント）
```

- 振込先口座は現状どおり`shops/{shopId}`内の配列でよい（件数が少ない）
- 台帳を1件ずつに分けるのは、1ドキュメント1MiB上限を避けるためと、更新時に全件書き込みを避けて書き込み回数を節約するため
- 台帳の一覧は「直近N件＋ページ送り」で読み、全件を毎回読まない（読み取り5万回/日の無料枠に対して十分余裕はあるが、キャッシュ前提にする）
- `ken_lastbackup`は端末ごとの情報なのでlocalStorageに残す（Firestoreに入れない）
- 現行コードの`load*/save*ToStorage()`は、非同期の「データ層」関数に置き換える。画面側は`await`で呼ぶ形に整理し、Firestore依存をデータ層1か所に閉じ込める（テストでは差し替えやすくなる）

### B. 採番の方式（項目4）

- 現行の「保存した時点でのみ高水位マークを進める」仕様（`commitInvNo()`）を踏襲する
- 「台帳に保存」時に**Firestoreトランザクション**で`shops/{shopId}`の`invoiceSeq`を+1し、そのまま請求書ドキュメントを作成する（番号の採番と保存を同じトランザクションにして、端末が複数あっても重複・欠番を防ぐ）
- お客様コード（`customerSeq`）も同様
- トランザクションはオンライン時のみ成立する。**新規の伝票No確定はオンライン必須**とし、オフラインで新規保存しようとした場合は「通信できません。接続後に保存してください」と案内する（入力内容は端末に残す）

### C. オフライン方針・同時編集の扱い（項目5）

| 場面 | 方針案 |
|---|---|
| 閲覧・既存データの編集（オフライン） | Firestoreのオフラインキャッシュ（`persistentLocalCache`、複数タブ対応）を使い、一度開いたデータは通信なしでも見られる。編集は端末に保存され、復帰時に自動で同期される |
| 新規保存（伝票No確定） | オンライン必須（上記B） |
| 同じ請求書を2端末で同時に編集 | Firestoreの標準は「後から書き込んだ方が勝つ」。上書きで他端末の変更が消えるのを防ぐため、請求書に`updatedAt`（またはversion）を持たせ、**保存時にトランザクションで読み込み時点の値と比較**する。食い違っていたら「他の端末で更新されています」と表示し、「最新を読み込む」「自分の内容で上書き」を選ばせる |
| オフライン中の同時編集 | トランザクションが使えないため、同期時は後勝ちになる。1店舗・スタッフ2名＋社用PCの低頻度の利用では許容し、注意書きを出す方針案 |
| 顧客・車両の編集 | 項目単位でぶつかる可能性は低いため、後勝ちのまま（`updatedAt`は記録しておく） |

### D. 認証・セキュリティルール

- Googleログイン。利用許可は`shops/{shopId}.allowedEmails`（スタッフ2名分。社用PCの運用が決まり次第、必要なら追加）で管理し、ルールで`request.auth.token.email in allowedEmails`かつ`email_verified == true`の場合のみ読み書き可とする（デフォルトは全拒否）
- 「顧客の個人情報が丸見えになる」リスクが最大のため、ルールはエミュレータで「ログインなし／許可外のGoogleアカウント／許可済み」の3パターンを自動テストしてから公開する
- 要確認（技術リスク）：iPhoneのホーム画面追加（PWA）起動時のGoogleログイン（ポップアップ／リダイレクト）の挙動。実機で検証が必要。`authDomain`をHostingの独自ドメインに揃えるなど対策を設計時に決める
- 要確認：Firebase SDKの読み込み方法。現行は「CDN読み込み＋SRI」方針だが、FirebaseのモジュールSDKはES module（import）で、SRIをかけにくい。**ビルドで1ファイルにバンドルし、Hosting（同一オリジン）から配信する**案が有力。「HTML1ファイル完結」方針は「ビルド成果物を配信する」形に改める必要がある（CLAUDE.md・共通ルールの更新が必要）

### E. 既存データの移行手順（項目7）

1. 移行前に、現行アプリの「バックアップJSON」を必ず書き出して保管する（ロールバック用）
2. 新アプリにGoogleログイン後、**1台だけ（お父さんのメイン端末）**で「クラウドへ取り込み」を実行する。複数端末から取り込むと重複するため、他の端末ではlocalStorageを取り込まない
3. 取り込みは、localStorageの内容、またはバックアップJSONファイルのどちらからでも可能にする（`restoreJSON()`相当の検証・正規化処理を流用）
4. 既存のid（伝票No・顧客コード・車両id）をそのままドキュメントIDに使い、**何度実行しても重複しない（冪等）**作りにする。書き込みは500件ごとのバッチ。取り込み後に`invoiceSeq`/`customerSeq`を既存の最大値に合わせる
5. 取り込み後、件数を現行データと突き合わせて確認する画面を出す
6. しばらくは旧アプリ（localStorage版）を読み取り専用で残し、問題がなければ停止する

### F. 車検証の写真保存とBlazeプラン（項目7）

- 前回調査では、Cloud Storage（画像などのファイル保存）は**2026-02-03以降Blazeプラン必須**（出典は公式FAQ。無料枠は5GBまで）。Blazeはクレジットカード登録が必要な従量課金プランだが、Firestoreと同じ無料枠は引き続き付く
- 現行アプリには写真保存機能がない。**初回リリースでは写真保存を対象外にし、Spark（無料）プランで開始**することを提案する
- 将来写真を保存する場合の選択肢：
  1. Blazeへ切り替え、Cloud Storageに保存する（予算アラートを設定する。金額は使用量次第のため公式の料金表で再試算する）
  2. 小さく圧縮した画像をFirestoreに文字列で保存する（Sparkのまま可能。ただし1ドキュメント1MiB上限・読み取り量が増えるので枚数が少ない場合のみ）
- 車検証は個人情報を含むため、保存するなら他人から見えないルール設計が必須
- ※料金・無料枠は、この環境から公式ページを開けず第三者サイトで確認した値のため、**契約前に公式で再確認**する

### G. 派生版（`ケンズ請求書アプリ/`、`kzs_`）への適用（項目7）

- 派生版は本リポジトリに含まれておらず（ローカルの別フォルダ）、今回は中身を確認できていない
- 提案：**まずケンズオートで完成・安定運用させてから**派生版へ展開する。コードは`shopId`前提で作り、店舗固有の値（localStorageプレフィックス、Firebase設定）を外に出して流用しやすくする
- 販売先ごとの個人情報を扱うため、**販売先ごとにFirebaseプロジェクトを分ける**案を推奨（データ・課金・アクセス権の分離。1プロジェクトで`shopId`だけで分ける案は、ルールの誤りが他店舗に波及するため非推奨）
- 派生版の仕様差分は、次回以降に実物を確認してから判断する
